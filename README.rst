Manual payment vouchers for cobranzas
-------------------------------------

Backend app to register one payment voucher per proof (bank transfer,
check, echeck, cash deposit, retention certificate, cash, unsupported,
or seller deposit). Each voucher owns sequence, chatter, optional
image/PDF designated proof (``message_main_attachment_id`` on chatter
``ir.attachment``; no Binary ``attachment`` field), a required Customer
(``partner_id`` on ``res.partner``; Char identification is gone;
``seller_deposit`` stamps a seeded sentinel partner), and a ``draft`` →
``validated_seller`` → ``validated_collections`` lifecycle (ORM/UI
default ``draft``; MCP stamps ``validated_seller``; Collections only via
Document Review Approve; no Reject). Collection sheets group a seller’s
vouchers through ``open`` → Confirm → ``proposal`` → Close → ``closed``
(Proposal or Closed may Cancel to ``cancelled``; Cancelled may Open back
to ``open``). Seller Close writes ``submitted`` (Submitted by Seller;
PDF Rendida) on the five-state statusbar. Sheets have their own chatter
and activities. The sheet form notebook is Allocations, Vouchers, and
Debt. Operators print a Planilla de Cobranza from a sheet: bound Print
PDF (``qweb-pdf``, A4 portrait, company letterhead) and header Export
XLSX share ``_collection_report_data()``. Sheet recon inputs are
``commission_percent`` (0–100), ``cash_on_hand``, and
``commission_withheld`` (frozen while closed or cancelled). Allocation
lines carry required ``document_kind`` (``invoice`` / ``quotation``,
default ``invoice``). Print includes draft allocations and vouchers;
``mismatch`` flags when voucher totals disagree with allocation
``total_vouchers``.

Per-company Collection Settings (``res.company`` + related
``res.config.settings``; XMLID
``collection.action_collection_config_settings``) control enabled
sellers (empty = none for new work), auto-create sheet (default ON),
allowed document types, Document Review, and the active
``collection.connector``. Settings users can Import sellers from that
connector (create/match/bind, then replace the enabled list). Voucher
(``COL/``) and sheet (``CS/``) sequences are per company. Customer
bindings (``collection.connector.customer.binding``) map an external
customer to a partner; internal users may create them (``1,0,1,0``) and
MUST never ``sudo()``.

MCP ``create_collection_vouchers`` still takes per-payment
``customer_identification`` strings and returns
``{vouchers:[{id,name,state,document_id},...]}``. On all-new create
only, the server lazily resolves each string into ``partner_id`` and MAY
create a ``res.partner`` plus customer binding. Exact replay ignores a
changed customer string and keeps the first-call partner. Each payment
may nest ``raw_ocr`` and ``seller_confirmed`` (typed review fields; both
omitted leaves empty provenance). MCP ``get_seller_id`` resolves
``{seller_id}`` from a WhatsApp/mobile among the company's enabled
sellers. MCP ``list_collection_customers`` and ``customer_debt`` MUST
NOT create partners. ``list_collection_customers`` still returns
``{customers}``. ``customer_debt`` still returns
``{customer, summary, invoices}`` with unchanged gross ``balance`` /
``total_balance`` / ``overdue_balance`` / ``open_balance``; it also
includes ``invoices[].allocatable_balance`` and summary
``total_allocatable_balance``, ``open_allocatable_balance``, and
``overdue_allocatable_balance`` (gross minus draft and confirmed
reservations, clamped at zero). MCP ``get_collection_sheet_pdf`` takes
only ``seller_id`` and returns the seller's open Planilla de Cobranza as
``{sheet, filename, mimetype, content_base64}``, or ``{sheet: null}``
when there is no open sheet. Coordinated Nebula tool
``register_latest_collection_voucher`` calls
``create_collection_vouchers`` only.
