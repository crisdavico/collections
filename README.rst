Manual payment vouchers for cobranzas
-------------------------------------

Backend app to register one payment voucher per proof (bank transfer,
check, echeck, cash deposit, retention certificate, cash, seller
deposit, or seller commission). Each voucher owns sequence, chatter,
optional image/PDF designated proof (``message_main_attachment_id`` on
chatter ``ir.attachment``; no Binary ``attachment`` field), a required
Customer (``partner_id`` on ``res.partner``; Char identification is
gone; ``seller_deposit`` and ``seller_commission`` stamp seeded sentinel
partners), and a ``draft`` → ``validated_seller`` →
``validated_collections`` lifecycle (ORM/UI default ``draft``; MCP
stamps ``validated_seller``; Collections only via Document Review
Approve; no Reject). Collection sheets group a seller's vouchers through
``open`` → Seller Close → ``submitted`` (Submitted by Seller; PDF
Rendida) → Confirm → ``proposal`` → Close → ``closed``. Submitted,
Proposal, or Closed sheets may Cancel to ``cancelled``; Reinstate brings
a ``cancelled`` sheet back to ``submitted``. Sheets have their own
chatter and activities. The sheet form notebook is Allocations,
Vouchers, and Debt. Operators print a Planilla de Cobranza from a sheet:
bound Print PDF (``qweb-pdf``, A4 portrait, no company letterhead or
printed date) and header Export XLSX share
``_collection_report_data()``; the workbook never turns typed text into
a formula or a link. Sheet recon inputs are ``commission_percent``
(0–100) and ``commission_withheld`` (frozen while closed or cancelled;
never negative); ``cash_on_hand`` (Cash to Administration) is derived,
not typed: cash vouchers minus ``seller_deposit`` vouchers minus
``commission_withheld``. Allocation lines carry required
``document_kind`` (``invoice`` / ``quotation``, default ``invoice``).
Print includes draft allocations and vouchers; ``mismatch`` flags when
voucher totals disagree with allocation ``total_vouchers``.

Money rules. An allocation's collected money (``total_vouchers``) is the
receipt values on its own receipts plus the full amount of each voucher
pointing at it whose money was never placed on a receipt, so a voucher
split across customers counts once, where its values are. A line cannot
apply more than the invoice balance it snapshotted; one ERP document
cannot be applied above its largest snapshotted balance across the
company's non-cancelled sheets; a receipt cannot apply more than its
values. An approved (``validated_collections``) voucher keeps its
amount, payment details, customer, company, currency, and destination
account: replacing its designated proof sends it back to Document Review
(giving back any cash it replaced), and on closed or cancelled sheets
the proof cannot change at all. A draft allocation can be deleted only
while its sheet is open or submitted and it has no issued receipt, cash
replacement, or agent revision. The commission voucher Confirm mints
stays in step with the declared commission after a Cancel and Reinstate.

Per-company Collection Settings (``res.company`` + related
``res.config.settings``; XMLID
``collection.action_collection_config_settings``) control enabled
sellers (empty = none for new work), auto-create sheet (default ON),
allowed document types, Document Review, and the active
``collection.connector``. Administrators, and Collections Managers from
Company Collection Settings, can Import sellers from that connector: it
creates, matches, and binds users inside the company only, adds them to
the enabled list, refuses an empty answer, and keeps enabled sellers
missing from the answer (they are named in a warning for a manager to
disable). Voucher (``COL/``) and sheet (``CS/``) sequences are per
company. Customer bindings (``collection.connector.customer.binding``)
map an external customer to a partner; Collections Users may create them
(``1,0,1,0``) and MUST never ``sudo()``.

Access follows two roles. **Collections User**
(``collection.group_collection_user``) is for back-office operators and
the MCP API user: Document Review, allocations, the receipt proposal
board, and Confirm. It may create contacts (no edit or delete) so new
customers can be bound without ``base.group_partner_manager``. Plain
internal users (CRM users, and the password-less seller identities that
Import creates) get no access to collection data; sellers act only
through the agent. Close, Cancel, and Reinstate need a Collections
Manager, and the server checks the role, not only the button. The
**Collections Manager** group (``collection.group_collection_manager``)
implies Collections User and grants collection configuration without
system administration; the administrator is a manager on install. Under
Collections → Configuration, **Company Collection Settings** edits only
the current company's collection options and imports sellers within that
company. **Connectors** provides company-scoped CRUD and a **Connector
Settings** dialog for SQLite/Bejerman settings, connection testing, and
Bejerman snapshot refresh. Credentials, the web service URL, TLS
options, the CA bundle, and the SQLite path are shown and written only
for administrators. Connector operations are server-side only
(``@api.private``); Test Connection checks for an administrator or a
Collections Manager. **Company Bank Accounts** manages only bank
accounts belonging to the user's allowed companies. Company record rules
continue to apply to vouchers, sheets, allocations, receipts, and
connector bindings. Privileged configuration writes use fixed field
lists after checking the caller's manager group and company access;
collection operations and MCP tools never elevate. Workflow guards are
internal server-side scopes: a context key sent over RPC or by an MCP
tool cannot open them. Creating a company or user is an explicit
database setup step, so installing the module does not create business
companies or login credentials.

Receipts are typed into the ERP by hand. Once that is done for a closed
sheet, a Collections Manager marks it **Entered in the ERP** (undo
allowed; Cancel clears it), and the filter **Pending ERP entry** lists
closed sheets still waiting. Until a sheet is marked and a connector
refresh that started after the mark has succeeded, its applied amounts
keep being subtracted from the ERP balances the agent sees; cancelled
sheets are never subtracted.

MCP ``create_collection_allocation`` takes a top-level
``customer_identification``, the payments, and the receipts that split
them, and returns the sheet, the vouchers, and the draft allocation. On
all-new create only, the server lazily resolves the identification into
``partner_id`` (by CUIT digits among commercial partners) and MAY create
a ``res.partner`` plus customer binding. A replay answers only the
seller that wrote it and only with the same content: a reused
``request_id`` needs the same payments, receipts and customer, and a
reused ``document_id`` the same seller and payment fields; anything else
is a generic conflict. Each payment may nest ``raw_ocr`` and
``seller_confirmed`` (typed review fields; both omitted leaves empty
provenance). MCP ``get_seller_id`` resolves ``{seller_id}`` from a
WhatsApp/mobile among the company's enabled sellers. MCP
``list_collection_customers`` and ``customer_debt`` MUST NOT create
partners. ``list_collection_customers`` returns ``{customers}``.
``customer_debt`` returns ``{customer, summary, invoices, as_of}``:
``as_of`` says when the connector's copy of the ERP was taken, and a
copy older than the connector allows is refused. The summary's
``total_balance`` is net of open credit notes (``gross_total``,
``credit_total``, ``net_total``), with ``overdue_balance`` and
``open_balance``; invoice rows keep their gross ``balance`` and add
``allocatable_balance``, with summary ``total_allocatable_balance``,
``open_allocatable_balance``, and ``overdue_allocatable_balance`` (gross
minus the reservations described above, clamped at zero). MCP
``get_collection_sheet_pdf`` takes only ``seller_id`` and returns the
seller's open (else submitted) Planilla de Cobranza as
``{sheet, filename, mimetype, content_base64}``, or ``{sheet: null}``
when there is neither. Every tool requires a Collections User caller and
can be bound to a trusted seller header (see Configure).

Configuration
=============

Production setup
----------------

1. **API user.** Give the user behind the agent's MCP API key
   **Collections User** only. The agent's tools never need Collections
   Manager (Close, Cancel, Reinstate, connectors, settings) and never
   need administrator rights.
2. **Tools.** The agent needs only the collection tools:
   ``get_seller_id``, ``list_collection_customers``, ``customer_debt``,
   ``get_collection_allocation``, ``create_collection_allocation``,
   ``get_collection_sheet_pdf``, ``close_collection_sheet``,
   ``declare_collection_cash`` and ``create_seller_deposit``. The
   generic muk_mcp write tools (``create_records``, ``update_records``,
   ``delete_records``, ``call_method``) accept a caller-supplied
   ``context`` and arbitrary writes on any model the API user can reach,
   which skips every check the collection tools make. At the pinned
   muk_mcp version an API key has no per-tool switch, only a ``read`` or
   ``write`` scope, and the collection write tools need ``write``. So
   expose only the collection tools to the model in the gateway's MCP
   client, and keep the API user's rights to Collections User.
3. **Seller identity.** Set the trusted seller header (below) and deploy
   the matching Nebula change, so the gateway, not the model, names the
   seller.
4. **Upgrades.** Upgrading a database that already had ``collection``
   installed cuts plain internal users off collection data (menus,
   vouchers, sheets, snapshots, board events) until they are added to
   Collections User or Collections Manager. Assign the groups as part of
   the upgrade.

Collection configuration
------------------------

Open **Collections → Configuration** for the current company's full
settings page:

- **General:** automatic sheet creation, document review and allowed
  document types.
- **Sellers:** enabled sellers, imported commission rates and **Import
  Sellers**.
- **Bank Accounts:** company accounts and **Manage Bank Accounts**.
- **Integration:** active connector, **Configure Connection**, **Test
  Connection** and **Manage Connectors and Mappings** for
  seller/customer mappings.

Use the normal **Save** and **Discard** controls. Collection Managers
can configure their company without system administration rights.
Administrators also see the advanced trusted seller header; connector
credentials remain administrator-only. The header applies to all
companies. The old configuration submenu entries are inactive after
upgrade; their actions remain available for existing links.

Trusted seller header (MCP agent)
---------------------------------

By default every collection MCP tool acts for the ``seller_id`` the
agent sends (for ``get_seller_id``, the ``mobile``). The agent is a
language model, so that value is only as trustworthy as the conversation
that produced it. The MCP API key's user must be a Collections User; any
other caller is refused.

To bind the tools to the verified WhatsApp sender instead, an
administrator sets **Collections → Configuration → Integration →
Advanced → Trusted seller header** (``ir.config_parameter`` key
``collection.mcp_trusted_seller_header``) to the name of an HTTP header,
for example ``X-Sender-Phone``. Empty, the default, keeps the behavior
above.

Contract for the gateway (Nebula) once a header name is set:

- **Source.** The gateway adds the header to every MCP HTTP request it
  forwards, with the phone of the verified WhatsApp sender taken from
  the channel metadata. The value comes from gateway code, never from
  model output or tool arguments, and the gateway drops any incoming
  header of the same name. Anyone holding the MCP API key can send any
  header, so the key must live only in the gateway.
- **Value.** The sender's phone in any Argentine format. It is
  normalized like ``get_seller_id``: non-digits are stripped, then one
  leading ``54``, then one leading ``9``. ``+54 9 11 5555-0199``,
  ``5491155550199`` and ``1155550199`` name the same seller.
- **Match.** The number must belong to exactly one internal user who is
  on the current company's Enabled Sellers list. The tools then act for
  that seller.
- **Arguments.** ``seller_id`` and ``mobile`` may be omitted. When the
  agent still sends one, it must name the header's seller.
- **Fail closed.** A missing or empty header, an unknown, ambiguous or
  not-enabled phone, or a ``seller_id``/``mobile`` naming another seller
  is refused with one generic error,
  ``The seller identity could not be verified.``, that never tells which
  sellers exist. A disabled seller can no longer close a sheet or
  declare cash through the agent.
