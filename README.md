# Collections

Odoo 19 app for **cobranzas**. Sellers report customer payments through a WhatsApp agent
(MCP tools); back-office operators review the proofs, reconcile money against customer
debt, and close each seller's collection sheet. Customer debt comes from an ERP
connector (Bejerman in `collection_connector_bejerman`; a dev-only SQLite sample in
`collection_connector_sqlite`).

> [!NOTE] `README.rst` is generated by `oca-gen-addon-readme` from the `readme/`
> fragments. This `README.md` is the short human guide; the full domain rules live in
> [AGENTS.md](AGENTS.md) and the normative behavior in `openspec/specs/`.

## Concepts

| Model                   | What it is                                                                                                                                                                                                          |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `collection.voucher`    | One payment (bank transfer, check, e-check, cash deposit, retention certificate, cash, seller deposit, seller commission) with an optional image/PDF proof. `draft` → `validated_seller` → `validated_collections`. |
| `collection.sheet`      | A seller's batch: `open` → `submitted` (Seller Close) → `proposal` (Confirm) → `closed` (Close); Cancel / Reinstate. Marked **Entered in the ERP** once its receipts are typed into the ERP.                        |
| `collection.allocation` | One per sheet and customer: debt lines snapshotted from the connector, applied amounts, receipts and receipt values, immutable revisions.                                                                           |
| `collection.connector`  | Company-scoped source of sellers, customers and debt. Adapters live in separate addons.                                                                                                                             |

Money rules worth knowing: approved vouchers are frozen (a proof swap sends them back to
review); applied amounts are capped per invoice line, per ERP document and per receipt;
"collected" per customer comes from receipt values; allocations that hold ledger rows
cannot be deleted.

## Roles

| Who                                                      | Can do                                                                                                                                                           |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Plain internal users (CRM users, seller identities)      | Nothing in Collections. Sellers act only through the agent.                                                                                                      |
| **Collections User** (operators, the MCP API user)       | Vouchers, Document Review, allocations, the receipt-proposal board, Confirm, Close, Cancel, Reset to Open; read-only connector data; create (not edit) contacts. |
| **Collections Manager** (implies User; admin on install) | Reinstate, Entered in the ERP, connectors, seller import and enablement, company settings.                                                                       |
| Administrators                                           | Connector credentials and system fields (user, password, WS URL, TLS, CA bundle, SQLite path) and the trusted seller header setting.                             |

Workflow guards cannot be bypassed with request context: server code opens guarded paths
through `collection_common.privileged()` scopes only.

## Install

This repository is aggregated into the Seedian Doodba project by
`odoo/custom/src/repos.yaml` (`./crisdavico/collection`, tracking `main`). From the
Seedian repo root:

```bash
invoke start
invoke install -m collection
```

Depends on `base`, `mail`, `muk_mcp` and `web`. Upgrading a database that already had
this module cuts plain internal users off until they are given a Collections group.

## Agent tools (MCP)

Read: `get_seller_id`, `list_collection_customers`, `customer_debt`,
`get_collection_allocation`, `get_collection_sheet_pdf`. Write:
`create_collection_allocation`, `close_collection_sheet`, `declare_collection_cash`,
`create_seller_deposit`. The caller must be a Collections User. When the trusted seller
header is configured, every tool acts for the seller whose verified phone the gateway
sends, never for a seller the model chooses.

Production setup (API user, trusted header, which tools to expose to the model):
[readme/CONFIGURE.md](readme/CONFIGURE.md).

## Tests and lint

From the Seedian repo root, on a scratch database:

```bash
docker compose run --rm -T --entrypoint odoo odoo -d collection_test \
  --stop-after-init --workers=0 --test-enable -i collection --test-tags /collection
```

On an already-installed devel database use `invoke test -m collection --mode=update`.
This repository has its own pre-commit hooks: `pre-commit run --all-files`.
